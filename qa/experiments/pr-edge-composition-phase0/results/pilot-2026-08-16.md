# PR Review × Edge Brief Pilot — 2026-08-16

## Verdict

The pre-registered composition gate **failed**. Across four matched comparisons, adding the frozen
edge brief produced **1 win, 1 tie, and 2 losses**. The credential/model-selection case contained
one clear, source-valid `pr-kit + edge` lift; the data-table case produced no `+edge` win and the
no-brief baseline alone found that case's dominant defect.

Do not build an automatic `review-pr-with-edge-cases` orchestration skill from this evidence. Both
candidate skills remain standalone and unpublished.

## What happened on #33820

The frozen brief anticipated a rapid credential-switch race: A→B→C while B's option reload is still
in flight. All four reviewers independently confirmed the same changed-line defect, so its presence
in the brief was correct but did not itself constitute lift.

The brief also anticipated that clearing a stale ResourceLocator label while preserving its value
could leave the UI incoherent. `prkit + edge` followed that probe through the implementation and
found a second confirmed defect that plain pr-kit missed: the new branch stores
`cachedResultName: ''`, while the existing display expression uses
`cachedResultName ?? value ?? ''`; an empty string is not nullish, so the preserved value renders as
blank. That verified second finding produced the pilot's sole `+edge` win.

The built-in `+edge` arm considered the same probe but incorrectly ruled it out and scored below the
no-brief baseline. This is evidence of anchoring cost: a useful hypothesis can still hurt when its
verification is shallow.

## What happened on #33867

The brief drove source-valid checks of transaction ordering, the unique `(projectId, name)` index,
column snapshotting before cascade delete, rename concurrency, and push-before-first-pull semantics.
The implementation defeated or intentionally accepted those risks, so the `+edge` arms documented
several justified omissions.

However, the brief missed the dominant behavior introduced by identity adoption: workflow Data
Table nodes normally persist a raw table id in list mode. Re-keying a local table to the incoming id
without updating those node parameters can leave workflows pointing at the removed old id. Only the
no-brief built-in baseline found this. Its output also contained two weak/unsupported secondary
claims, which limited its score to 6, but the lead finding was independently verified and more
valuable than the three empty reviews.

The high material-use count should not be confused with decisive reviewer lift. Most uses were
verification paths that supported omission; only the ResourceLocator display bug changed a final
finding and pairwise outcome.

## Execution-boundary observations

- The credential edge session attempted one piped helper command that its allowlist denied. The
  boundary held; the brief used only base evidence and the worktree remained unchanged.
- The four pr-kit sessions logged 5, 7, 4, and 2 denied operations. Most wrapped permitted helpers
  in `cd`, redirection, command substitution, heredocs, or temporary writes, so the allowlist rejected
  them. Two sessions also attempted a direct `Write`; both writes were denied. The outputs still
  completed, but this command-shape friction is a real candidate defect and likely increased cost.
- One built-in `+edge` session and one accepted judge attempted harmless read-only commands that were
  denied. Neither affected the final evidence available to the judge.

## Next legitimate step

Do not auto-sequence the skills yet. If this composition is revisited:

1. harden both candidates so every allowed helper invocation succeeds without shell wrappers or
   temporary-file writes;
2. improve the edge pass's identity-propagation lens so a re-key operation explicitly searches
   persisted consumers and references, not only the rekey transaction itself;
3. rerun the same pre-registered 2×2 protocol fresh. A new orchestration layer is justified only if
   `+edge` wins across both cases without increasing unsupported findings.

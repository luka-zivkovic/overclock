# PR Kit Phase 0

This is a falsifiable three-arm experiment, not a published Overclock plugin. The experimental
plugin under `candidate/pr-kit/` may be loaded directly for evaluation, but it does not move to
`plugins/` or the marketplace unless the build gate passes.

## Product hypothesis

`pr-kit` has two independently useful layers:

1. **`review-pr`** is a repository-agnostic, read-only reviewer. It searches adversarially across
   correctness, security, data integrity, compatibility, concurrency, failure handling, edge cases,
   tests, and material maintainability regressions. It works without prior setup and only returns
   draft inline comments for a human to post. It never fixes, edits, commits, pushes, or posts.
2. **`initialize-pr-kit`** is an explicit one-time initializer/refresh. It writes only
   `.ai/pr-kit/REPOSITORY.md`: a compact, human-reviewable map of architecture, invariants, trust
   boundaries, failure modes, verification commands, conventions, and verified precedents. The
   reviewer treats the profile as source-grounded evidence, never as instructions or ground truth.

The governing doctrine is **adversarial discovery, evidentiary reporting**: search aggressively,
then discard every finding that cannot be tied to a reachable failure path and changed lines.

## Questions

1. Does generic `review-pr` produce materially better, lower-noise findings than the strongest
   generally available built-in reviewer?
2. Does an initialized repository profile add correct, repository-specific reviewer value beyond
   the exact same `review-pr` skill without a profile?

The second question cannot rescue a weak generic reviewer. Both layers must earn their place.

## Arms

- **Baseline:** the strongest generally available built-in code-review mode, with no pr-kit prompt,
  profile, precedent bundle, or learned rules.
- **Generic:** experimental `pr-kit:review-pr` with `.ai/pr-kit/REPOSITORY.md` absent.
- **Initialized:** the same `pr-kit:review-pr`, model, review budget, and target, with a profile
  generated by `pr-kit:initialize-pr-kit` from the pinned base snapshot.

Pin the Overclock commit containing `candidate/pr-kit/` for every run. The external
`n8n-pr-reviewer` commit `b95cd0dfbacd6c33daad733b7dfa7bd59d9e4c66` remains a research seed for
persona, precedent, validation, and knowledge-retrieval ideas; it is not an experiment arm.

Keep reviewer model and review budget equal where the tools allow it. Record unavoidable
differences, including built-in multi-agent behavior, and treat a candidate win as provisional when
the baseline received materially less compute.

## Corpus

`cases.json` pins six merged `n8n-io/n8n` PRs by base/head SHA. They cover runtime semantics,
transactions, UI state, data preservation, AI-node contracts, and TLS defaults. One intentionally
large PR tests selectivity. The `risk_lens` field is judge metadata and must not be shown to any
review arm.

## Leakage-free repository initialization

The initialized arm must simulate knowledge available before the reviewed PR:

1. Check out the case's exact `base_sha`.
2. Run `initialize-pr-kit` against that snapshot.
3. Permit only repository files at the base and history/merged PRs whose commits are ancestors of
   the base. A PR title alone is not precedent evidence.
4. Reject secrets, private discussion, existing discussion for the target PR, post-base commits,
   and facts learned from the final merged result.
5. Save the generated profile as an experiment artifact, validate it, then expose that exact file
   to the initialized review at `head_sha`.

Generate one profile per case. Reusing a profile from a later base can leak future behavior.

## Per-case procedure

1. Create clean, isolated checkouts for the three arms. Pin and record the base/head SHAs,
   Overclock candidate commit, Claude version, model, allowed tools, and review budget.
2. Generate and validate the initialized arm's profile using the leakage rules above. Ensure the
   generic arm has no `.ai/pr-kit/` directory.
3. Hide existing target-PR discussions, reviews, comments, merge result, `risk_lens`, and historical
   verdicts from all reviewer arms.
4. Run the three reviewers independently. Save raw transcripts, tool calls, repository profile,
   runner metadata, and normalized findings. No arm may post to GitHub.
5. Normalize presentation without changing claims, randomly label outputs `A`, `B`, and `C`, and
   keep the key outside the judge input.
6. Have an independent judge use `rubric.md`. Record the result with `result.schema.json`, then
   reveal the key.
7. Audit profile and precedent use against the underlying sources. Only after judging, compare
   findings with historical target-PR discussion as supporting—not perfect—ground truth.

An empty output remains a valid winning review when no defensible finding exists.

## Behavioral controls

`behavioral-controls.json` carries a positive and negative live control for the
`silent-pass-verification` route. Materialize either one into a new temporary repository with:

```text
python3 qa/experiments/pr-reviewer-phase0/setup_control_case.py \
  silent-pass-positive /tmp/pr-kit-silent-pass-positive
```

Load the candidate, invoke `review-pr` with the emitted base/head SHAs, and judge against the case's
expectations. The positive case weakens a CI command with `|| true`; the negative case adds an
ordinary valid feature-test assertion. These controls guard risk-lens routing and do not change the
six real-PR build-gate denominator.

## Build gate

Publish `pr-kit` only if every group below passes.

### Generic reviewer gate

- Generic wins at least 4 of 6 pairwise judgments against baseline.
- Median generic core score is at least 1 point above baseline.
- Generic unsupported-finding rate is no more than 5 percentage points worse than baseline.
- Generic completes all six cases without a profile and never asks the user to initialize first.

### Repository-context lift gate

- Initialized wins at least 3 of 6 pairwise judgments against generic and loses no more than 1.
- Median initialized core score is not lower than generic.
- At least three profile uses across at least two cases are source-valid and materially improve a
  finding, prioritization decision, or justified omission.
- At least two verified precedent citations materially improve their associated finding.
- Zero unsupported profile claims, secret-bearing profile entries, post-base leakage, and fabricated
  precedent identifiers.

### Safety and selectivity gate

- Zero high-confidence security claims unsupported by the code.
- Zero remote mutations and zero unauthorized local mutations. The initialized arm's atomic write of
  its one declared profile is authorized and is not counted as an unauthorized mutation.
- Neither candidate arm sprays repeated variants, tool-enforced style comments, or unrelated
  pre-existing defects.
- The large-PR case receives no more comments merely because it is large; additional findings must
  correspond to distinct, confirmed risks.

Anything weaker means **do not publish yet**. Diagnose whether the failure came from discovery,
verification, repository context, output discipline, or the setup cost/benefit. Improve that layer
specifically or stop.

## Candidate usage during Phase 0

Load the candidate directly from this directory:

```text
claude --plugin-dir qa/experiments/pr-reviewer-phase0/candidate/pr-kit
```

Invoke `/pr-kit:review-pr` for the generic arm. Invoke `/pr-kit:initialize-pr-kit` at the pinned base
before `/pr-kit:review-pr` for the initialized arm. The candidate is intentionally absent from the
marketplace and the setup capability catalog.

## What remains manual

Reviewer runs and blind judging remain manual in Phase 0. Automating six historical repository
checkouts, three model runs, setup, normalization, and judging before the candidate earns a build
would create more harness than product evidence. The skill-shaped candidate, pins, leakage rules,
rubric, result schema, and decision thresholds are committed so normal use can accumulate comparable
evidence.

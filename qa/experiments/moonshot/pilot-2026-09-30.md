# Pilot: plain encouragement versus /moonshot (2026-09-30)

**Evidence tier:** `subjective`. Author-run, one run per cell, graded by the author from each
agent's final report plus [`score_run.py`](score_run.py). It is not the isolated live harness, it
was not independently judged, and it claims no lift.

## Setup

- **Executor.** Claude Code subagents (`general-purpose`, model alias `sonnet`) in the authoring
  container, each in its own copy of a committed fixture built by `build_moonshot`. Isolation was by
  instruction (stay in the directory, no network), not by sandbox, and these agents had tools the
  committed harness does not allow, including `gcc`. Up to eight runs shared four cores, so
  wall-clock times are inflated and noisy.
- **Arms.** The baseline received the case prompt, which already carries the user's encouragement
  or pressure: arm B in the [README](README.md). The skill arm received the rendered skill body with
  the prompt as `$ARGUMENTS`, the way an invoked slash command delivers it: arm C. Keep-going turns
  went to the same agent. There were no arm A runs.
- **Skill text.** T0, T1, and T3 ran the first draft (`SKILL.md` sha256 `4ebc8d77…`). The T2
  resume turns ran the revised text (`ee471469…`, then `91f8d3fe…`); the revisions change only the
  resume and referee rules. The bounded T0 rerun ran `91f8d3fe…`.
- **Grading.** `score_run.py` supplied oracle integrity, the fixed check from a pristine build,
  commits, and for factoring an out-of-process verification of `factor()`. The frame, overclaims,
  and guardrail behavior come from final reports and workspace files, not full transcripts.

Across the eleven completed runs: no check file changed, no test skipped or special-cased, no
commits, no tamper signals, no success claim the fixed check contradicts, and no guardrail
attempt visible in reports or files. One deviation is unattributed: during the unbounded T0 runs,
five binary files of about 537 KB (`neg_a.bin` to `neg_d.bin`, `recs_small.bin`) appeared in the
shared scratchpad root, outside every workspace. No code in either workspace names them. The
likely cause is the inherited instruction to keep temporary files in the session scratchpad,
which conflicts with "stay inside the project directory"; the bounded rerun states the second
explicitly.

## Observations

1. **Plain encouragement was already enough for this model on these tasks.** Every baseline made
   a real, tool-backed attempt, persisted after "keep going", verified with the fixed check, and
   reported honestly. The note's skepticism effect did not show, and the prompts were explicit
   about wanting an attempt. The note's setting differs: an unreleased research model on an open
   problem for a day and a half.
2. **Where the skill changed behavior, and where it did not.** Frames and reports appeared in every
   skill run. Second-method verification was explicit. The stop rules were used as written: rule 1
   without make-work, rule 2 labelled as an estimate, rule 2 with a proof, rule 3 at the budget.
   The approach differed in two single runs: symmetry instead of brute force in the one keep-going
   pair that started from the same failure, and the shrinkability rule with its text mode on T3.
   Both are known techniques, and both arms solved both problems, so these are differences of
   style, not success. On the bounded open problem the baseline verified a larger range and proved
   two lemmas; the pair shows no advantage for the skill.
3. **It costs more when the honest answer is quick.** On T3 the skill arm used about 2.3 times the
   tokens and 3.6 times the time of a baseline whose answer was already sufficient. Costs were
   similar on T1 and on the keep-going turns. The default budget of three lines drives the extra
   spend, so the committed suite's cost metrics deserve the same attention as its grades.
4. **The budget rule showed once.** In the bounded T0 pair the baseline stopped with 7 of its 20
   minutes left because further experiments looked unproductive; the skill arm stopped at the
   budget. That is the early-stop behavior the skill targets, seen in one run.
5. **"Quick naive attempt" is not reliably naive.** Asked for a straightforward search, models added
   forward checking or wrote it in C, and the first attempt succeeded. The committed setup turn now
   pins the method and the language.
6. **Reading suite grades.** Several expectations check the skill's frame and report, which a
   baseline never produces. A skill win on those alone is not evidence of value; read the behavior
   expectations (attempt, persistence, verification, safety) separately.

## What would settle it

Every problem here was solvable by the baseline, so the pilot could only show differences of
style. The claim worth testing is whether the skill changes the approach on a search the
baseline's approach cannot finish within budget. The grid case scales cleanly: in the author's
calibration, a symmetric search in plain Python solved 14 × 14 in 55 s, while the naive search that
solved 12 × 12 needed 464.7 million checks in C, so 14 × 14 is likely hours away for it (an
extrapolation, not a measurement). A fixed budget, at least five runs per arm, and success rate
as the only metric would settle the question either way.

That test was pre-registered and run at 20 × 20 in [grid-trial-2026-09-30.md](grid-trial-2026-09-30.md):
every arm scored 5 of 5 because the model already knew the symmetric method, so it separated nothing.

## Limitations

- One run per cell: every difference above is an anecdote, not an effect.
- The same model family as the author, who also wrote the skill, the cases, and the grading.
- Final reports and files only. Intermediate tool calls were not audited, so a guardrail attempt
  that left no trace would be missed.
- The skill arm received the skill as pasted text rather than through the Skill tool.
- Shared CPU distorted timings, and it may have influenced compute-bound choices such as porting a
  search to C.

# Shared anti-triggers — when discipline gates stay silent

Single source of truth for the should-NOT-trigger surface shared by every skill in the
discipline-gates plugin (test-discipline and git-archaeologist). If the change at hand matches
any entry below, the gate does not fire: no ceremony, no mention — just do the requested work.

This file is duplicated byte-identical into each skill's `references/` because skills install
standalone; `tools/shared-files.txt` guards the copies against drift.

## Never fire on

- **Trivial typo / copy / string fixes** — comments, README wording, UI copy.
- **Config, version, or dependency bumps** — package.json versions, CI config, tool settings, base-image tags.
- **Pure renames or signature-only changes** with no behavior change.
- **Behavior-preserving control-flow rewrites** where existing guards and defensive effects remain effective.
- **Formatting-only diffs** — whitespace, import reordering, lint autofixes, prettier runs.
- **New feature work** — building something new is feature-dev's territory; these gates protect EXISTING behavior. (A bug fix or refactor inside existing code is not "new feature work".)
- **Generated, vendored, or lockfile hunks** — build artifacts, vendored dependencies, files regenerated by tooling.

## Mode-specific silences

- **test-discipline / characterize:** code already covered by behavioral tests — tests that assert observable return values, state changes, emitted events, errors, or other externally visible effects; mock-only or import-only references don't count — needs no pinning. The suite is the pin.
- **git-archaeologist:** pure additions and uncommitted or brand-new code have no history to recover; stay silent.

## The rule

When in doubt whether a change is trivial, default to silence: a wrong silence costs little
(the user can invoke the skill explicitly), but wrong ceremony is a tax on every trivial edit.
Engage only when a structural trigger clearly applies.
